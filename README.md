# Gift Sniper — Tonnel

Telegram-бот на inline-кнопках: следит за коллекциями подарков на Tonnel
Marketplace — и в обычных лотах, и в аукционах — и присылает алерт, если
позиция заметно дешевле рынка: либо дешевле медианной цены по коллекции,
либо дешевле последней продажи NFT с точно таким же Model + Backdrop +
Symbol.

Управление полностью на кнопках. При добавлении слежки бот задаёт два
вопроса: на сколько % дешевле рынка алертить (кнопки) и до какой цены в
TON искать офферы (текстом, либо «Без лимита»).

## Переменные окружения

| Переменная  | Обязательна | Что это                          |
|-------------|-------------|-----------------------------------|
| `BOT_TOKEN` | да          | Токен бота от [@BotFather](https://t.me/BotFather) |
| `PROXY_URL` | нет (но почти всегда нужна на облачном хостинге) | Резидентский прокси для запросов к Tonnel — см. раздел ниже |
| `PROXY_MAX_CONCURRENT_PER_ADDR` | нет (по умолчанию `1`) | Сколько запросов бот одновременно пускает через один и тот же адрес прокси — см. раздел про ошибку 503 ниже |
| `TONNEL_MAX_RETRIES` | нет (по умолчанию `3`) | Сколько раз повторять запрос к Tonnel при сетевой/прокси-ошибке |
| `TONNEL_RETRY_DELAY_SECONDS` | нет (по умолчанию `1.5`) | Задержка между повторными попытками (растёт линейно: 1.5с, 3с, ...) |
| `TONNEL_REQUEST_TIMEOUT_SECONDS` | нет (по умолчанию `25`) | Сколько ждать один запрос к Tonnel, прежде чем считать его зависшим и пойти на повтор |

## Локальный запуск

```bash
pip install -r requirements.txt --break-system-packages
export BOT_TOKEN="твой_токен"
python bot.py
```

## Деплой на Railway (без компьютера, прямо с телефона)

1. Залей этот репозиторий на GitHub (см. ниже, как это сделать без ПК)
2. На [railway.app](https://railway.app) → New Project → Deploy from GitHub repo → выбери репозиторий
3. В настройках проекта → Variables → добавь `BOT_TOKEN` со своим токеном
4. Railway сам подхватит `Procfile` и запустит бота как worker-процесс — деплой пойдёт автоматически при каждом пуше в GitHub

## Как залить на GitHub без компьютера

1. Установи приложение **GitHub** (App Store / Google Play) или открой github.com в браузере телефона
2. Создай новый репозиторий (кнопка "+" → "New repository")
3. Внутри репозитория: "Add file" → "Create new file" — и по очереди создай каждый файл из этого набора, вставляя содержимое через копирование текста
4. Готово — репозиторий у тебя на GitHub, дальше подключаешь его к Railway (шаг выше)

## Как работает добавление слежки

1. Кнопкой выбираешь коллекцию (или пишешь свою через «Другое»)
2. Кнопкой выбираешь порог — на сколько % дешевле рынка алертить (10/15/20/30%)
3. Бот спрашивает: **до какой цены в TON искать офферы?** Пишешь число
   текстом (например `15` или `15.5`) — или жмёшь «♾ Без лимита», если
   верхней границы нет
4. Готово — бот каждые `POLL_INTERVAL_SECONDS` (по умолчанию 2 минуты)
   проверяет и обычные лоты, и аукционы этой коллекции, и присылает алерт
   только на то, что одновременно (а) дешевле рынка на заданный % и (б)
   укладывается в твой лимит по цене

## Подключение резидентского прокси

Tonnel закрывает Cloudflare-проверкой запросы с датацентровых IP — а IP
Railway (и почти любого другого облачного хостинга) как раз датацентровый.
Без прокси рано или поздно (обычно почти сразу) все запросы начнут падать
с 403, и бот не сможет ничего проверить. Резидентский прокси решает это,
потому что его IP выглядит как обычный домашний/мобильный.

**Как подключить:**

1. Купи резидентский прокси у любого провайдера (нужен именно HTTP(S)
   прокси, не SOCKS5) — провайдер выдаст тебе host, port, и обычно
   логин/пароль
2. В Railway → Variables добавь переменную `PROXY_URL` со значением в
   любом из этих форматов — бот сам разберётся, какой именно ты вставил:
   - `http://user:pass@host:port` — уже готовая ссылка
   - `user:pass@host:port` — без схемы, бот сам добавит `http://`
   - `host:port:user:pass` — частый формат у провайдеров резидентских прокси
   - `host:port` — если у прокси вообще нет логина/пароля
3. Передеплой — и все запросы к Tonnel пойдут через прокси

**Несколько прокси сразу.** Если провайдер выдал не один адрес, а
несколько (например, разные порты для параллельных сессий), можно
перечислить их через запятую: `PROXY_URL="прокси1,прокси2,прокси3"`. Бот
будет перебирать их по кругу между запросами — это особенно полезно
вместе с `SCAN_CONCURRENCY` > 1, когда несколько коллекций сканируются
параллельно и им есть смысл не толкаться в одну и ту же прокси-сессию.

**Если что-то пошло не так.** Нажми «🔍 Проверить» у любой слежки — если
дело в прокси, в отчёте будет видна ошибка соединения (пароль прокси в
логах и в этом отчёте всегда скрыт — бот его маскирует перед показом).

### Ошибка «CONNECT tunnel failed, response 503»

Это ошибка на уровне ШЛЮЗА ПРОКСИ, а не самого Tonnel и не логики бота:
прокси-провайдер не смог поднять туннель до Tonnel и ответил 503. Чаще
всего причина одна из трёх:

- у прокси-сессии закончился трафик или истекло время сессии — стоит
  проверить личный кабинет провайдера;
- шлюз провайдера временно перегружен — обычно проходит само за несколько
  секунд/минут;
- **тариф прокси не даёт нескольких одновременных соединений**, а бот
  за один скан коллекции параллельно шлёт 3-4 запроса (лоты по двум
  сортировкам + история продаж + аукционы) — если настроен всего один
  адрес в `PROXY_URL`, они все бьют в один и тот же прокси разом.

Бот теперь сам:
1. ограничивает число одновременных запросов через один адрес прокси
   переменной `PROXY_MAX_CONCURRENT_PER_ADDR` (по умолчанию 1 — то есть
   строго по очереди на каждый адрес);
2. повторяет неудавшийся запрос до `TONNEL_MAX_RETRIES` раз (по умолчанию
   3) с растущей паузой, каждый раз беря следующий адрес из `PROXY_URL`,
   если их несколько.

Если ошибка всё равно повторяется — это сигнал, что дело именно в самом
прокси (кончился трафик/сессия, либо у провайдера сбой), и стоит либо
проверить прокси в личном кабинете, либо взять несколько адресов
(`PROXY_URL="прокси1,прокси2"`) вместо одного.

## Если бот "не пересылает офферы"

В «Мои слежки» у каждой слежки есть кнопка **🔍 Проверить** — она сразу
сканирует коллекцию и присылает отчёт: сколько лотов/аукционов нашлось,
какая получилась медиана, сколько алертов ушло и почему (или сразу
показывает текст ошибки запроса к Tonnel, если она есть — и если это
похоже на сбой прокси, отчёт это отдельно отметит). Это самый
быстрый способ понять, реально ли сейчас на рынке нет ничего подходящего
под твой порог/лимит, или дело в ошибке API — не нужно лезть в логи
Railway с телефона.

Если у коллекции несколько раз подряд не получилось получить данные с
Tonnel, бот сам один раз напишет об этом в чат.

## Настройки (переменные окружения либо константы в начале bot.py)

| Переменная                          | По умолчанию | Что регулирует                                    |
|--------------------------------------|--------------|----------------------------------------------------|
| `POLL_INTERVAL_SECONDS` (env)        | 120          | Как часто пересканировать все слежки (сек). Можно поменять в Railway → Variables без правки кода |
| `SCAN_CONCURRENCY` (env)             | 3            | Сколько слежек сканировать параллельно за раз (больше = быстрее цикл, но выше риск 403 от Tonnel) |
| `PROXY_URL` (env)                    | не задан     | Резидентский прокси для запросов к Tonnel (один адрес или несколько через запятую) — см. раздел «Подключение резидентского прокси» |
| `PROXY_MAX_CONCURRENT_PER_ADDR` (env) | 1            | Сколько запросов бот одновременно пускает через один и тот же адрес прокси — см. раздел про ошибку 503 |
| `TONNEL_MAX_RETRIES` (env)           | 3            | Сколько раз повторять запрос к Tonnel при сетевой/прокси-ошибке |
| `TONNEL_RETRY_DELAY_SECONDS` (env)   | 1.5          | Задержка между повторными попытками (линейно растёт) |
| `TONNEL_REQUEST_TIMEOUT_SECONDS` (env) | 25         | Сколько ждать один запрос к Tonnel, прежде чем считать его зависшим |
| `MIN_LISTINGS_FOR_STATS`             | 5            | Минимум лотов в объединённой выборке, чтобы считать медиану честной. Если данных меньше — сравнение с медианой пропускается, но сравнение с последней продажей и аукционы всё равно проверяются |
| `SALES_HISTORY_LIMIT`                | 50           | Сколько последних продаж запрашивать для сверки     |
| `AUCTIONS_LIMIT`                     | 30           | Сколько активных аукционов запрашивать за раз (максимум у tonnelmp) |
| `PRESET_COLLECTIONS`                 | список из 17 | Коллекции-кнопки в меню "Добавить слежку"           |
| `THRESHOLD_OPTIONS`                  | 10 / 15 / 20 / 30 | Варианты порога "насколько дешевле" на кнопках |

Пример в Railway: Variables → добавь `POLL_INTERVAL_SECONDS=60` — бот
подхватит новое значение после следующего редеплоя/рестарта.

## Известные ограничения

- Схема запросов к Tonnel основана на документации пакета `tonnelmp` от
  сообщества — не проверялась в реальном окружении разработчиком этого
  бота, мелкие расхождения возможны при первом запуске.
- Медиана считается по объединённой выборке price_asc + latest (до ~60
  уникальных лотов) — честнее, чем по одним только самым дешёвым лотам,
  но всё равно не полный рынок: у tonnelmp жёсткий лимит 30 записей за
  один запрос.
- Структура ответа `getAuctions()` в документации пакета не расписана
  построчно (в отличие от `getGifts()`). Бот перебирает несколько
  вероятных названий поля с текущей ставкой (`current_bid`, `currentBid`,
  `price` и т.д.) — если алерты по аукционам не приходят, стоит посмотреть
  логи (warning с сырым словарём) и поправить список ключей в
  `_AUCTION_PRICE_KEYS` / `_AUCTION_ID_KEYS`.
- `getAuctions()` не поддерживает сортировку по цене и ограничен 30
  результатами за запрос — при большом числе активных аукционов часть
  дешёвых лотов может не попасть в выборку. Ограничение самого `tonnelmp`.
- При отслеживании сразу многих коллекций Tonnel может временно
  ограничивать частые запросы (403). Стандартный интервал проверки — 5 минут.
- Аукцион — это живой торг: к моменту, когда ты откроешь ссылку, цена
  могла уже вырасти. Алерт по аукциону — это сигнал «стоит посмотреть», а
  не гарантия зафиксированной цены.
- Ретраи и ограничение параллельности на прокси (см. выше) помогают при
  временных сбоях, но не могут исправить прокси, у которого реально
  кончился трафик/сессия, или который провайдер держит недоступным дольше
  нескольких секунд — в этом случае нужно чинить сам прокси.
- Таймаут на запрос (`TONNEL_REQUEST_TIMEOUT_SECONDS`) не может по-настоящему
  прервать зависший синхронный вызов внутри потока — Python не умеет
  насильно останавливать поток. Он лишь перестаёт ЖДАТЬ такой вызов, чтобы
  не подвесить весь скан навсегда; сам поток в редких случаях может
  доработать в фоне уже без дела.
